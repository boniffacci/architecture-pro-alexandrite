# Выбор и настройка мониторинга в системе

## 1. Мотивация

В текущей архитектуре компании «Александрит» мониторинг ограничен Яндекс Метрикой, которая отслеживает только поведение пользователей на сайте. С ростом нагрузки, подключением внешних API и увеличением количества заказов становится критически важным:

- Контролировать состояние ключевых сервисов: онлайн-магазин, CRM и MES.  
- Предотвратить потерю заказов и задержки в обработке.  
- Обеспечить прозрачность SLA для внешних клиентов и внутренних операторов.  
- Позволить команде DevOps и разработчикам оперативно выявлять узкие места в системе. 
- Давать бизнесу **объективные данные для принятия решений** — например, о необходимости масштабирования, переработки функционала или инвестиций в оптимизацию.   

Мониторинг поможет компании минимизировать жалобы клиентов и сохранить доверие B2B-партнёров и B2C-клиентов.

---

## 2. Выбор подхода к мониторингу

Для разных частей системы выбираем подходы с учётом задач:

- **Онлайн-магазин и CRM API** — подход **RED** (Rate, Errors, Duration):  
  - Ориентирован на пользовательские запросы и SLA.  
- **MES и расчёт стоимости заказов** — подход **USE** (Utilization, Saturation, Errors):  
  - Ориентирован на внутренние ресурсы и эффективность работы операторов.  
- **RabbitMQ** — подход **USE** для контроля очередей и сообщений в flight.  
- **Инфраструктура и базы данных** — «Четыре золотых сигнала» (latency, traffic, errors, saturation).

## 3. Выбираемые метрики

| Метрика | Для чего нужна | Ярлыки / теги |
|---------|----------------|---------------|
| Number of dead-letter-exchange letters in RabbitMQ | Контроль потерянных сообщений | queue_name |
| Number of messages in flight in RabbitMQ | Проверка загруженности очередей | queue_name |
| Number of requests (RPS) для всех API | Нагрузка на сервисы | service_name, endpoint |
| Number of requests per user для всех API | Определение «тяжёлых» клиентов | user_id |
| CPU % для всех API | Загруженность серверов | service_name, instance_id |
| Memory Utilisation для всех API и БД | Выявление нехватки ресурсов | service_name, instance_id |
| Response time (latency) для всех API | SLA, UX, выявление узких мест | service_name, endpoint |
| Number of HTTP 500 для всех API | Ошибки сервисов | service_name, endpoint |
| Number of simultanious sessions | Загруженность сессий | service_name |
| Kb transferred / provided для всех API | Анализ трафика и пропускной способности | service_name |
| Size of S3 storage | Контроль расхода диска | bucket_name |
| Size of shop / MES db instance | Контроль роста данных | db_name |
| Number of connections для БД | Проверка лимитов соединений | db_name |

Дополнительно:  
- Мониторинг очередей и worker-сервисов MES для асинхронной обработки заказов.  
- Трассировка запросов через OpenTelemetry/Jaeger для выявления узких мест и «тяжёлых» заказов.

## 4. План действий

1. **Создать инфраструктуру мониторинга**  
   - Time-series база: Prometheus для метрик.  
   - Grafana для визуализации.  
   - Alertmanager для оповещений.  

2. **Интеграция сервисов**  
   - Онлайн-магазин, CRM, MES → экспортеры метрик.  
   - RabbitMQ → exporter очередей и сообщений.  
   - Базы данных → node-exporter / cloud-exporter.  

3. **Настройка метрик и дашбордов**  
   - Разделение по сервисам и пользователям.  
   - Дашборды для DevOps, операторов MES и менеджеров.  

4. **Настройка алертов**  
   - Время отклика > SLA → отправка уведомления в Slack/Email.  
   - Ошибки 500 → создание тикета в системе поддержки.  
   - Очереди RabbitMQ превышают threshold → масштабирование worker-инстансов.  
   - CPU/Memory > 80% → уведомление DevOps + автоматическое добавление инстанса при возможности.  

5. **Трассировка критических операций**  
   - Подключение OpenTelemetry для end-to-end анализа запросов.  
   - Отслеживание времени обработки сложных 3D-заказов.  

---

## 5. Пороговые значения насыщенности

| Метрика | Порог | Действия при превышении |
|---------|-------|------------------------|
| CPU % | 80% | Отправка алерта DevOps, возможное горизонтальное масштабирование |
| Memory Utilisation | 80% | Алерт + проверка утечек памяти, добавление инстансов |
| Number of messages in flight | > 1000 | Алерт, запуск дополнительного worker-сервиса |
| Response time (latency) | > 3 сек (shop API), > 2 сек (CRM API), > 5 сек (MES API) | Алерт, проверка «тяжёлых» заказов, анализ трассировки |
| Number of HTTP 500 | > 1% от запросов за 5 минут | Создание тикета, уведомление команды разработки |
| Size of DB / S3 | > 90% | Плановое увеличение объема, алерт для админов |

> В случае превышения порогов система должна автоматически уведомлять команду DevOps, создавать тикеты в баг-трекере и при возможности запускать автоматическое масштабирование сервисов для снижения нагрузки.
