# Архитектурное решение по логированию

## Мотивация

В настоящее время ошибки и нестандартные ситуации выясняются исключительно со слов клиентов. Это сильно замедляет работу разработчиков и службы поддержки.  

**Зачем нужно логирование:**
- Позволяет оперативно выявлять и устранять ошибки.
- Уменьшает нагрузку на службу поддержки.
- Обеспечивает системный сбор данных для анализа работы сервисов.
- Облегчает поиск причин зависаний, ошибок или некорректной работы заказов.

**Технические метрики:**
1. Количество ошибок (ERROR) по сервисам.
2. Количество предупреждений (WARN) о нестандартных ситуациях.
3. Время реакции на критические ошибки.
4. Среднее время восстановления сервисов после ошибки.
5. Количество повторных обращений клиентов по одной проблеме.

**Бизнес-метрики:**
1. Сокращение времени обработки инцидентов.
2. Снижение количества жалоб клиентов.
3. Повышение SLA по обработке заказов.

**Приоритетные системы для логирования и трейсинга:**
- MES API и MES — высокая критичность для процесса производства.
- Shop API и CRM API — для контроля заказов и взаимодействия с клиентом.
- Очереди сообщений (RabbitMQ) — для отслеживания потерянных сообщений.

## Предлагаемое решение

**Технологии и компоненты для логирования:**
- **ELK Stack (Elasticsearch + Logstash + Kibana)** — хранение, анализ и визуализация логов.
- **Fluent Bit / Fluentd** — сбор логов с контейнеров и микросервисов.
- **Alertmanager / Grafana** — алерты по критическим событиям.
- **Logback / SLF4J / Spring Boot Logging** — внедрение логирования в код сервисов.

**Типы логов:**
- INFO — нормальные события (создание/изменение заказа, вход пользователя).
- WARN — нестандартные ситуации (повторная попытка записи в БД, превышение времени ожидания).
- ERROR — критические ошибки (сбой обработки заказа, упавший сервис, потеря сообщения).
- DEBUG — только для разработки или диагностики по требованию.

**Пример логирования (уровень INFO):**
2025-10-14 14:22:01 INFO OrderService: Order created. OrderID=12345, CustomerID=98765

**Политика безопасности и хранения логов:**
- Доступ к логам имеют только разработчики и специалисты поддержки с ролью «Support».
- Чувствительные данные (PII) маскируются в логах.
- Логи хранятся в отдельных индексах для каждого сервиса.
- Срок хранения: 90 дней, с последующим архивированием.
- Размер индекса ограничен 50 ГБ, с ротацией и сжатием.

**Анализ логов и алертинг:**
- Настройка алертов на критические ошибки и превышение порогов.
- Поиск аномалий, например резкое увеличение количества ошибок или заказов, возможный DDoS.
- Интеграция с Grafana для визуализации логов и метрик.

## Итог

Внедрение централизованного логирования позволит:
- Быстро выявлять и устранять ошибки.
- Снижать нагрузку на поддержку.
- Анализировать работу сервисов и процессы заказов.
- Настроить алертинг и систему раннего обнаружения аномалий.
